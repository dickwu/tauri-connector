# v0.17.6

This patch release fixes what the 0.17.5 retests turned up: commands right after a reload, background windows, concurrent screenshots, port selection and version drift. Unknown-outcome quarantine and the rule against replaying dispatched scripts are unchanged.

## Bug fixes

- **Commands sent after a reload never run on the old page.** A script that calls `location.reload()`, assigns `location` or submits a form marks the page as navigating. Until the new document is up, later commands are refused before they start with `page_navigating` (or `page_not_ready` when the new runtime does not come up within the deadline), both `retryableBeforeDispatch: true`. Nothing is replayed: a script that started is never sent again.
- **Deadline refusals are typed.** A command that keeps hitting an unready page until its deadline reports `page_navigating` / `page_not_ready` with `retryable: true` and `execution: not_dispatched`, not a bare deadline error.
- **Background windows fail fast without quarantine.** When the target window is unfocused, hidden or minimized, the plugin first sends a 1.5 s liveness probe. A page that does not answer gets `window_not_visible` and the command is never sent, so the window is not quarantined. If the probe goes unanswered right after a navigation started, the refusal is `page_navigating` instead, because the old document is simply being replaced.
- **Screenshots during a reload are retryable.** A capture that loses its page (`capture_context_changed`, `page_navigating`, `page_not_ready`, a closed page channel) is retried up to 3 times. After that it reports `page_navigating`, never `outcome_unknown`. The default `screenshot` no longer falls back to the legacy renderer for page or contention errors (`window_not_visible`, `page_navigating`, `page_not_ready`, `resource_busy`, `outcome_unknown`, quarantine), so you no longer get a misleading "snapdom not available". The fallback is now only for hosts that cannot serve protected capture at all.
- **Concurrent screenshot and eval queue instead of failing.** A command that needs a window lease another command holds now waits for it (up to 15 s, within its own deadline) instead of failing at once with `resource_busy`. A quarantined window still fails immediately.
- **One screenshot shape for every source.** `default`, `--source auto`, `webview_native`, `window_native` and `dom_rendering` all print `viewportCrop` (`basis`, `rectPx`, `windowPx`), `artifact`, `overwrote`, `requestedPath` and `resolvedFromCollision`. `artifact`, `path` and `requestedPath` are `null` when nothing was written.
- **No more false `capabilities_path_pattern` failure in doctor.** When `build.rs` sets `capabilities_path_pattern` (inline, through a `const`/`let` or a `format!`), doctor looks in every capability directory it names and in non-default capability directories, nested ones included. If any capability there grants `connector:default`, it no longer reports that `app.add_capability` is missing.
- **`status` and `windows` share exit codes.** `status` exits `0` when it selected an app and `1` when it could not (`connected: none`, `ambiguous_app`, `project_mismatch`, ...). It prints the full report either way. This matches `windows`, `eval` and the other app commands.

## New

- **Port ranges from the environment.** The plugin reads `TAURI_CONNECTOR_PORT_RANGE` (WebSocket), `TAURI_CONNECTOR_MCP_PORT_RANGE` and `TAURI_CONNECTOR_BRIDGE_PORT_RANGE` as `START-END`, and these win over the builder. `TAURI_CONNECTOR_PORT` / `TAURI_CONNECTOR_MCP_PORT` set only the start port (the range runs from START to START+100). The CLI and the standalone MCP server read `TAURI_CONNECTOR_PORT_RANGE` too, so their port scan finds apps moved off 9555–9655. See README "Plugin Configuration" and SETUP.md.
- **Version warnings in `status` and `doctor`.** Both warn, with the exact fix, when more than one `tauri-connector` with different versions is on `PATH` (`multiple_cli_versions`), when the CLI and the connected app's plugin differ (`cli_plugin_version_mismatch`), or when the local Homebrew tap formula is older than the CLI (`homebrew_tap_stale`). `status --json` returns them as `versionWarnings`.

## Dependencies

- Cargo (both lockfiles): aws-lc-rs 1.18.2 → 1.19.0, aws-lc-sys 0.46.0 → 0.47.0, unicode-width 0.2.2 → 0.2.3. Everything else was already at its latest compatible version, and `cargo outdated` shows no other spec bumps.
- npm: `package.json`, `cli/package.json` and `server/package.json` were already at their latest versions.
- GitHub Actions: actions/checkout v4 → v7, actions/setup-node v4 → v7, actions/upload-artifact v4 → v7, actions/download-artifact v4 → v8.
- Deliberate pins: `cairo-rs` and `gio` stay at 0.18 (latest 0.22) on Linux. They must match the gtk-rs 0.18 stack that webkit2gtk/wry use. CI stays on Node 22, per `engines`.

## Known limitations

- `webview_native` captures still do not render compositor-only effects such as `backdrop-filter`; use `--source window_native` for the composited pixels.

## Install

```sh
brew update && brew upgrade tauri-connector
# Or install the command-line packages directly:
cargo install connector-cli --version 0.17.6 --locked
cargo install connector-mcp-server --version 0.17.6 --locked
```

Host applications on `tauri-plugin-connector = "0.17"` pick up the fixes with `cargo update -p tauri-plugin-connector`, then a rebuild and restart of the app. The version warnings, the status exit codes, the doctor capability check, the CLI port-range scan, the screenshot retries and the legacy-fallback change are client-side. Navigation refusals, the background-window probe, the lease queue, the env port ranges and the uniform capture shape need the 0.17.6 plugin in the app.
