# v0.15.0 — Reliable application-owned workflows

Known multi-step operations can now run inside the Tauri application with strict targeting, local waits, result bindings and explicit verification. The application owns the run, so reconnecting or resubmitting the same `runKey` does not start another copy.

## New workflow APIs

- `workflow_run`, `workflow_get`, `workflow_cancel`, `workflow_resume` and `workflow_capabilities` are available through embedded MCP, standalone MCP and the `tauri-connector workflow` CLI.
- Strict role/label/test-ID/CSS locators, scoped targets, entity matching, replace/append input, queries and bounded conditions.
- Durable journal, checkpoint revision checks, safe continuation of undispatched work and read-only reconciliation. Uncertain writes retain resource isolation; completed writes are not automatically replayed.
- Shared application-side arbitration across workflow, legacy batch, CLI/WS and MCP; bounded, redacted outcomes and independently readable evidence pages.
- Host-enabled workflow authentication using `TAURI_CONNECTOR_WORKFLOW_TOKEN` or `ConnectorBuilder::workflow_token(...)` with at least 32 bytes. Credentials are outside the workflow spec and rechecked before dispatch.
- Updated README, setup instructions, bundled skills and a Bun workflow helper.

## Corrected behavior

- Wait timeouts and failed postconditions now report failure and block dependent batch actions. Ordinary business JSON containing `error` remains data.
- Targeted `fill` replaces the selected field; `type` appends. Native setters and synthetic input events update controlled components.
- Bridge fallback is only permitted before dispatch. Slow operations, execution errors and lost responses never trigger replay through the second transport.
- Pending request/listener cleanup covers timeout, disconnect, send failure and dropped futures.
- The standalone client explicitly enables Tokio's macro feature, so its published package builds without relying on workspace feature unification.
- Batch report-save failures retain the execution report with `persistenceWarning`. Saved screenshots use artifact references by default; explicit `save:false` preserves legacy inline output.
- `networkidle` explicitly reports unsupported instead of treating document completion as network idleness. IPC monitoring reports per-window desired/applied acknowledgements.

## Upgrade and boundaries

```sh
brew upgrade tauri-connector
# or
cargo install connector-cli --version 0.15.0 --locked
```

```toml
tauri-plugin-connector = { version = "0.15", optional = true }
```

```sh
npx skills add dickwu/tauri-connector
tauri-connector workflow capabilities
```

Legacy tool/batch inputs remain available, with intentional corrected failure semantics. CLI workflow status uses exit 0 for completed success, 1 for failure/cancellation, and 2 for incomplete or uncertain runs. A nonzero exit never authorizes replay of a write.

Workflow v1 supports strict sequential execution and synthetic DOM interaction. Observed UI state does not prove production business persistence. Restart history is readable; arbitrary restart replay, business receipt providers, workflow parallelism, transition assertions and general rollback are not supported. Durable workflow persistence currently requires supported Unix private-file semantics; Windows ACL support and native Windows/Linux WebView validation remain outstanding.
